# Worker TVM-FFI experiment

This standalone library evaluates TVM-FFI as the worker's sole Rust/Python interface. It has no PyO3 dependency and does not load the production worker extension. It uses the existing Rust worker codec, the repository's installed PyTorch and TVM-FFI packages, and ordinary PyTorch numerical callbacks.

`Executor` uses the production worker crate's native executor for admission, launch, completion and result delivery. `submit(batch_id, tensor)` accepts increasing batch numbers and returns a `Submission`. `poll(submission)` advances completion and delivers its tensor once, or returns `None` while GPU accesses remain pending. Capacity stays occupied until delivery, including after physical completion; a refused admission leaves its batch number available to retry. Independent ready results can be consumed while another batch is pending. There is no separate experimental execution queue.

Each numerical batch retains its DLPack input and result references, cancellation state and a CUDA event from the worker crate's shared CUDA module. A submission can query `retired()`, explicitly `wait()`, or `cancel()` its result. Cancellation retains the input through physical completion and reports its error when polled; callback failures follow the same completion and delivery path while preserving their exception type. Closing discards undelivered results and drains outstanding work before releasing the callable. Already delivered tensors remain usable. Dropping the executor also drains its batches, even when a caller retains a submission. Unknown physical completion retains affected tensors and the callable instead of releasing storage that the GPU may still access.

Public objects and methods are registered in `src/lib.rs` and `src/stream.rs`; Python classes contain no lifecycle implementation. Registration uses TVM-FFI's stable C API because the Rust derive resolves existing types and the Rust sys crate does not currently declare the registration entry points. FFI value conversion and reflection stay in these bindings. `src/execution.rs` uses native state, owning tensor references, and a numerical `Function`; it never reads Python attributes, events, or futures. `WorkerRequest` retains the existing native IPC enum and serializes through the shared codec without constructing Python request records. `RequestPool` uses the production worker crate's request implementation to apply admission and finish commands directly from this native message. That crate has no Python dependency; the production Python worker and this experiment use the same slot, epoch, pending-call, and progress mechanisms.

`HostLane` and `HostTask` bind the production worker crate's host executor. `submit(convert_func(callback))` runs Python work on a native Rust thread and returns a native task result. A host callback returns completed bytes, such as encoded media, or `None` for in-place input preparation. Tensor inputs stay inside the Python callable; returned bytes become an owned Rust value before crossing threads. Task admission, the shared queue, cancellation, waiting and observer registration use the same implementation as production. Cancelled queued work releases its unused capacity and callback inputs immediately. Running work finishes normally, and `close()` joins it before returning. Done observers receive the task and may read its result or submit another action.

`store_media_bytes(payload)` uses the production `MediaSource` owner to reserve a POSIX shared-memory segment and copy completed bytes. It returns the segment name and hands unlink responsibility to the receiver. No Python shared-memory object or resource tracker participates. Production results retain this native owner through execution cleanup and response serialization before making the same handoff.

`HostBuffers(tensors, device)` owns preallocated host inputs through the production worker's native buffer ring. Pass a CUDA device index for pinned copy sources, or `None` for synchronous CPU use. `acquire()` returns a slot and a DLPack tensor after that slot's previous copy completes; fill the tensor, enqueue its copy, and call `record_copy(slot)` inside the matching `tvm_ffi.use_torch_stream(stream)` scope. `close()` drains outstanding copies and releases the ring's tensor references. Returned views retain their allocations independently, and FFI containers can retain the ring after its original Python wrapper disappears. No additional Python buffer state or CUDA events are used.

`SharedBuffer(nbytes, consumers, device)` uses the production shared-memory owner. Its `tensor()` returns a DLPack byte view of the payload, and `name()` identifies the POSIX segment for readers. With a CUDA device, construct it in the intended `tvm_ffi.use_torch_stream(stream)` scope, call `begin_copy()` before submitting numerical copies and `mark_ready()` afterwards. The native stream callback announces readiness without Python; `settled()` also checks reader acknowledgments. `close()` drains writes, unregisters host memory and unlinks the name. Unregistration can wait for unrelated device work, so serving schedules it on a host executor. Tensor references retain the mapping independently of the producer object, without retaining its CUDA registration. Neither the buffer protocol nor a PyO3 adapter is needed for this path.

`SharedRead(name, nbytes, slot, offset, timeout)` claims a payload range and waits for readiness in Rust. Its `tensor()` exposes a DLPack byte view that retains the reader, so final tensor release acknowledges completion. Explicit `release()` requires all numerical reads to have ended. Failed readiness and timeout also return the acknowledgment. `open_shared_memory(name)` returns an owned read-only descriptor for ordinary codec file input; the caller closes it. Both operations use the production POSIX owner without interpreting its name as a filesystem path.

`VmmPool(storage)` binds the production export pool to caller-supplied exportable CUDA byte storage. `reserve(nbytes)` clears a chunk's reader header on the current FFI stream; retain that stream through pool closure. The returned `PoolChunk` supplies DLPack payload and acknowledgment views. `retire(chunk, consumers, producer, grants, export)` retains the range until producer completion and named reader acknowledgments, optionally withdrawing its descriptor grant when the range returns. `reap()` observes asynchronous readback without waiting for device completion. Explicit `release(chunk)` requires completed accesses. Close and final destruction drain the pool's device accesses; payload views retain their allocation independently. No Python pool state or event adapter participates.

`TransferPool(bytes, reads, workers)` uses the production native read pool and host executor. `submit(callback, destination, bytes)` reserves capacity, records the destination's current FFI stream and invokes the numerical callback on a native thread. The callback must retain its source and destination tensors and enqueue all CUDA accesses on the supplied stream handle; CPU callbacks receive zero. A returned `TransferTicket` exposes `ready`, `result`, `cancel`, `retirement_ready` and completion observers. `result()` joins its producer event onto the current FFI stream. Queued cancellation returns credits immediately; running reads retain their callback and credits through physical completion, including after cancellation or a numerical exception. Closing and final destruction join reads outside the GIL. DLPack tensor handles stay with the observing object; native tasks retain only a callable, native state and serialized errors, without adding `Send` or `Sync` to SDK tensor handles.

Pinned host copies use the shared `uniserve_kernels.peer_storage.copy_host_device` operator, as in production transport. The native ticket owns their lifetime. PyTorch's asynchronous `Tensor.copy_` instead records an external stream in its pinned allocator and may record an event there when the host tensor is later freed, after the transfer pool has already destroyed that stream. Numerical callbacks must not leave allocator references to pool-owned streams beyond pool closure.

`KVImporter(capacity, workers, device)` uses the production KV importer and native copy action. `reserve(request, input, request_pool_idx, reset, copy)` selects a KV input from a decoded `WorkerRequest` and returns a `KVImport`. Both numerical functions receive a workspace index and a native stream handle; their closures retain prepared source, destination and scratch tensors. CUDA callbacks select that stream with `torch.cuda.ExternalStream` and order their source dependencies before copying. Rust owns workspace admission, reset/copy sequencing, stream drain and retirement. `write.result()` reports numerical completion, `pool.adopt(write)` commits a successful result, and `pool.abandon(write)` discards it while outstanding accesses retain storage. `write.cancel()` withdraws a queued copy without adopting or abandoning its destination. `stop()` closes admission and joins copies outside the GIL. Native streams retain their CUDA contexts, including when constructed before PyTorch initializes the device. This experiment binds prepared numerical copies; transport reads and cache-page reservation are still exercised through the production integration suite.

`CUDAStream(device, handle, event_slots)` binds native submission fences to a borrowed numerical stream; `partition_streams(device, sm_counts)` creates owned Green Context streams. Both use the production stream owner. `fork()` retains the partition independently, and `handle()` supplies a PyTorch `ExternalStream` view. `wait()` orders execution after the producer selected by `tvm_ffi.use_torch_stream`; `record()` returns a native event for a later consumer join, or `None` when both streams are the same. The event retains its producer's SM partition after the stream closes. Event waits and readiness queries use the same native CUDA implementation as production.

`DescriptorGrants(endpoint)` and `fetch_descriptor(endpoint, export)` use the production native descriptor service. Registration retains an allocation descriptor until revocation; receiving transfers an owned descriptor to the caller, which closes it after importing the allocation. Rust serves the Unix socket without Python callbacks. FFI containers retain the service after individual wrappers disappear, and final destruction closes the endpoint and joins its thread. `tvm-ffi-methods.patch` installs reflected instance methods even when a metaclass defines the same name, such as `ABCMeta.register`; methods defined on the class or its bases still take precedence.

Resource destruction must let independent Python work proceed while draining GPU accesses. The experiment builds TVM-FFI v0.1.12 with `tvm-ffi-object-release.patch`: ordinary objects and `CAny` release their native references outside the GIL. `CAny` also takes the owned result of argument conversion directly, avoiding an extra reference that prevents destruction. Native shared ownership determines when resources close, including through FFI containers; Python wrapper finalizers do not close resources. Explicit `close()` remains available for deterministic shutdown. Unmodified TVM-FFI 0.1.12 holds the GIL during object disposal and can deadlock when device completion needs another Python thread.

The `Executor` numerical callback runs on the submitting thread. It must run one homogeneous batch on CPU or on the selected CUDA stream and device. For CUDA, enter both `torch.cuda.stream(stream)` and `tvm_ffi.use_torch_stream(stream)` around submission. The callback receives ordinary `torch.Tensor` arguments through `convert_func(..., tensor_cls=torch.Tensor)`. Polling only queries completion; it does not synchronize the host with pending GPU work. Delivered tensors are physically complete and can be consumed on another CUDA stream. Explicit waits and shutdown drain pending accesses. Tensor references retain allocations, while native executor delivery returns admission capacity.

Internal execution ownership uses ordinary Rust `Arc` and `Mutex`; it does not depend on the reflected object hierarchy. The pinned Rust SDK makes `Function` implement `Send` and `Sync`, which permits native host threads to invoke Python callbacks through TVM-FFI's interpreter entry. Its tensor, byte and error handles do not have those Rust traits. The experiment adds no `Send` or `Sync` implementations. FFI return values are converted on the host thread, and task results retain ordinary Rust bytes and error strings. Error transfer follows TVM-FFI's serialization representation: kind, message and backtrace. It preserves the exception type and callback frames, without retaining arbitrary native error payloads across threads. The Rust SDK has no public string constructor for `ErrorKind`, so the binding reconstructs the error through the stable C API on the observing thread.

The Rust dependency is pinned to upstream commit `df463f9bd269867fc7f4d578d62d80cc2a11d004`. The published `0.1.0-alpha.0` export macro lacks the unmangled symbol required for a loadable module; the pinned upstream macro exports it and contains panic-to-error handling. The isolated environment uses the repository's locked dependencies, including PyTorch, with only TVM-FFI replaced by the patched source build. Its wheel has a development version assigned by upstream's build system. The production environment and lockfile retain `apache-tvm-ffi==0.1.12` and `torch==2.13.0+cu130`.

From the repository root:

```bash
FFI_EXPERIMENT="$PWD/artifacts/rust-worker/ffi-retirement"
UV_PROJECT_ENVIRONMENT="$FFI_EXPERIMENT/venv" uv sync --locked --python /usr/bin/python3.12 --extra dev --extra test --extra bench --extra gpu --no-install-project
git clone --branch v0.1.12 --depth 1 --recurse-submodules --shallow-submodules https://github.com/apache/tvm-ffi "$FFI_EXPERIMENT/tvm-ffi"
git -C "$FFI_EXPERIMENT/tvm-ffi" apply "$PWD/experiments/worker-ffi/tvm-ffi-object-release.patch"
git -C "$FFI_EXPERIMENT/tvm-ffi" apply "$PWD/experiments/worker-ffi/tvm-ffi-methods.patch"
uv build --python "$FFI_EXPERIMENT/venv/bin/python" --wheel --out-dir "$FFI_EXPERIMENT/wheels" "$FFI_EXPERIMENT/tvm-ffi"
uv pip install --python "$FFI_EXPERIMENT/venv/bin/python" --no-deps "$FFI_EXPERIMENT"/wheels/*.whl

export PATH="$FFI_EXPERIMENT/venv/bin:$PATH"
cargo build --locked --manifest-path experiments/worker-ffi/Cargo.toml --target-dir "$FFI_EXPERIMENT/target"
cargo run --locked --manifest-path experiments/worker-ffi/Cargo.toml --target-dir "$FFI_EXPERIMENT/target" --example wire_fixture > "$FFI_EXPERIMENT/request.bin"
cargo run --locked --manifest-path experiments/worker-ffi/Cargo.toml --target-dir "$FFI_EXPERIMENT/target" --example kv_fixture > "$FFI_EXPERIMENT/kv-request.bin"
"$FFI_EXPERIMENT/venv/bin/python" -m pytest -q experiments/worker-ffi --ffi-library "$FFI_EXPERIMENT/target/debug/libuniserve_worker_ffi.so" --ffi-request "$FFI_EXPERIMENT/request.bin" --ffi-kv-request "$FFI_EXPERIMENT/kv-request.bin"
```

The full suite requires CUDA. It exercises CPU and GPU module execution, strided shared tensor storage, callback failure after device submission, cross-stream consumption, cancellation, capacity through result delivery, independent completion, concurrent Python callers, shutdown and executor destruction, and native request admission and retirement from an IPC message. The host tests cover native-thread PyTorch execution, byte results and in-place tensor writes, input reclamation, exception type and traceback, reentrant observers, and shutdown while Python work is pending. Warmup precedes checks that require outstanding GPU work, so first-use allocation or kernel loading does not turn them into synchronous calls. Generated libraries, messages, and logs belong under `artifacts/`.

Final-owner tests hold a CUDA stream behind a device gate. `HostBuffers`, `Executor`, `CUDAStream` and `VmmPool` must drain outstanding work during destruction while another Python thread releases that gate. Each resource is exercised through a direct reference, `Array` and `CAny`. A separate process contains deadlocks because an in-process timeout cannot reliably run when a native destructor holds the GIL. Existing shared-owner tests ensure that releasing one wrapper does not close another owner's resource.

`profile_retirement.py` captures the same lifetime boundary after CUDA Graph replay, using finite device work so both patched and unmodified dependencies can finish. Run the workload serially in each environment and inspect the `gil-held-wait` rule as described in [Execution profiling](../../docs/profiling.md):

```bash
nsys profile --trace=cuda,nvtx,python-gil --cuda-trace-all-apis=true --cuda-graph-trace=graph --sample=process-tree --cudabacktrace=sync:0,memory:0 --python-backtrace=cuda --export=sqlite --output="$FFI_EXPERIMENT/retirement" \
  "$FFI_EXPERIMENT/venv/bin/python" experiments/worker-ffi/profile_retirement.py --ffi-library "$FFI_EXPERIMENT/target/debug/libuniserve_worker_ffi.so"
.venv/bin/python -m uniserve.sanitizer trace "$FFI_EXPERIMENT/retirement.sqlite" --rule gil-held-wait
```

This capture diagnoses GIL ownership during GPU retirement; it is not a throughput measurement. Inspect recorded synchronization coverage as well as hints: a leaked reference can suppress destruction entirely and produce no wait to analyze.

This is a feasibility experiment, not a serving implementation or throughput result. Numerical callbacks execute through the production native executor, but consume prepared tensors rather than IPC call plans. Native request commands and host execution are exercised separately. Host callbacks produce completed CPU outputs; the experiment does not move owning FFI tensor handles or outstanding CUDA accesses into host tasks. The experiment does not replace production KV/latent pools, transfers, the IPC service loop, graphs, distributed collectives, or model loading. Adopting TVM-FFI for the worker requires moving those owners to native state and replacing their consumers together; forwarding their current Python attribute operations through callbacks would preserve the interpreter dependency this interface is intended to remove. End-to-end model, graph, cancellation, and AFD validation remains necessary for that replacement.
