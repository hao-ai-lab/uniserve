# Execution

UniServe schedules requests in Rust and executes numerical calls through a Python and PyTorch backend. Models expose computational capabilities through ordinary modules; the worker binds their attention, matrix multiplication and expert layers to execution resources. Request identities, KV allocations, sampling state, streams and CUDA graphs belong to the engine and worker.

`TensorStore.write`, `write_scalar` and `write_scalars` write numerical results into owned buffers; `commit_writes` makes the completed batch's results visible to subsequent calls. `Transport.export` returns a physical tensor locator, and `TensorExport` associates transport locations with a logical output. Consumers use `fetch` or `borrow`. `release` revokes further reads, while `retirement` completes only after device accesses and granted readers finish. KV transfers use the same export and retirement mechanisms.

Numerical consumers pass declared tensor values to `BatchState.export_tensors`. Rust selects this rank's bound writes and exports completed buffers through `TensorStore`, retaining completion signals directly and assembling native transfer descriptions. Resident tensor transfers and encoder-feature exports use the same implementation. The executor exports encoder features from the component's output rank after numerical writes; pure transfers never enter the numerical dispatcher. `BatchState.consume_tensor` shares resident input selection and read ownership with numerical image consumers. Python retains tensor copies, model evaluation and physical backend operations.

Asynchronous media tasks retain their deferred writes on the pending output after batch commit. Their completion callbacks fill the values and submit them through the same batch export operation. Encoded units supply only initialized rectangular regions, whose offsets include the rank's logical output offset. Successful deferred exports become visible together; a failed export revokes accepted locations and abandons the affected writes while physical accesses retain their existing retirement rules.

The native `Worker` owns each rank's model runner, request storage, KV and canvas state, latent pages, bounded product pools, transports and process groups. Construction loads and binds resources without warmup or IPC I/O. Explicit warmup prepares numerical execution and graph budgets once, before admission; direct calls and the bound service share one executor. Normal close drains readers, destroys graphs and releases their backing in dependency order, including the canvas state banks. Aborted close retains asynchronous resources until process exit and does not wait on GPU work or peers. The worker borrows its IPC endpoint, which remains open for its caller to close. Immutable configuration and advertised capacity remain available after worker closure.

`WorkerConfig` is an immutable native value shared by rank execution and capacity planning. Launch parsing resolves lane selectors to concrete calls once; the launcher and worker use the same lane type. Capacity fitting returns a resolved configuration with adjusted pool and input limits. Python execution code reads a view of those settings; backend-specific options stay with their numerical backend. Direct Python callers use `config.replace(...)` to derive a configuration without changing the original.

Native capacity planning builds one `WorkerLayout` before allocation. Its `WorkerInfo` supplies the engine's logical admission bounds; the layout also carries rank-local product backing, latent dimensions and fixed device reservations. KV sizing charges input buffers, request state, import workspaces, graph padding and graph storage before assigning the remaining whole units to the pool. An explicit token capacity must fit the same grant. Ranks sharing a pool select the smallest unit count that fits each rank.

Media workers price each candidate request count from the numerical state and product layouts. The output horizon changes with request concurrency, so memory requirements need not increase monotonically. Ranks reduce the complete vector of fitting candidates and select the greatest common count, including ranks that own products without denoising state. Numerical dimensions are read once per sizing pass; candidate arithmetic and the final report remain native. Python supplies tensor layouts, model descriptions and memory measurements. Direct Python callers materialize a report view when they read `Worker.info`; the executor consumes its native report directly.

After numerical preparation, Rust submits representative token, canvas and image requests through the serving executor. Startup assigns KV and latent pages within resident capacity; buffer spans use the same aligned byte allocator as the engine. `Free` and `Finish` complete before those addresses can be reused. Image warmup reads guidance from the prepared numerical trajectory. The native executor waits for completion without a Python polling loop, and resets batch numbering after all startup requests retire.

The worker's native `Executor` owns bounded batch admission, dependency ordering, collective launch order, completion, and result delivery. Direct Python callers and the rank service use the same submission path. Capacity remains occupied until the result is consumed, and a full queue leaves the submitted batch number available for retry. Independent requests can advance while another waits for storage; ranks sharing collective computation preserve launch order and wait for prior result delivery before starting the next batch.

The native `Service` receives typed requests from the rank channel, correlates responses and delivers independently ready batches. Close stops admission and drains accepted work before acknowledgment; fatal results stop admission too. Completion wakes interrupt channel waits, while outstanding remote acknowledgment words require polling. Expert ranks wait briefly for their own engine's next batch before joining an empty expert step, and closing ranks participate until every peer leaves. The service borrows the executor and channel for one synchronous run; their owners retain responsibility for resource closure.

The native executor selects per-operation numerical preparation, dispatches homogeneous forwards and binds their results on the worker thread. Dependency callbacks only notify a native `Submission` and wake the service; repeated or late notifications cannot launch a batch twice. Native `BatchState` owns the input set, aligned output rows and request index; numerical callbacks borrow its tensor views and capture descriptions. The executor reads those owners directly, binds rows from its decoded call plan, and closes resources without a Python cleanup callback. Completion predicates are read once after their copy fence, while device-gated predicates remain tensors. The production binding currently uses PyO3; the executor and request pool themselves have no Python dependency.

Each batch contains one call kind and component, with at most one call per request. Rust selects active rows from their pending outputs and dispatches the batch; a fully skipped batch proceeds directly to resource commit. Token, canvas and encoder calls execute one numerical step. For image diffusion, Rust advances each declared interval and selects its active calls and absolute solver steps. Rust resolves guidance prefixes and latent-bank accesses; Python builds numerical rows, evaluates the model and applies the mathematical solver. Only trajectories with an integrated prediction produce a latent result at the end of their interval. Producer batches launch before their consumers, and tensor products become readable at batch commit. Numerical dispatch needs no additional dependency graph or Python completion set.

For standalone video diffusion, Rust retains request slot views, submits host noise preparation, selects latent banks and dispatches denoising and reconstruction. A request retains its bound numerical ladder until the runner changes. Numerical helpers build schedules, draw noise, assemble condition tensors, evaluate model calls and reconstruct RGB or audio values. Rust records their results and exports final latents or decoded media through the same batch storage owner. Request retirement, explicit removal and pool closure wait for host writers before releasing slot storage.

Standalone diffusion uses the same native `Execution` and graph buckets as other numerical calls. `ModelExecutor` owns the denoiser and bounds serving layouts by request capacity, retiring the least recently used layout before admitting another. Startup prepares the maximum layout first, warms all layouts before any capture, and captures one step graph per configured layout. `Execution` retains layout buffers and immutable host index sources; replay supplies the committed latent bank, page indices, request slot and numerical step inputs. Additional serving layouts run eagerly and allocate outside captured pools. Retiring layout constants waits for their queued readers. Ordinary modules and denoisers share stream dependency handling on both successful and exceptional returns. Python retains tensor allocation, numerical views, model evaluation and solver updates.

The native backend applies request commands and resolves each call's predecessor before preparing tensors. Newly admitted slots reset together, including slots admitted before a later Start fails. Rust checks computation support, placement and resource bounds and retains predecessor ordering. Unread predecessor outputs can retire before input acquisition, while outputs consumed by this batch remain visible through launch. Input leases close after numerical execution, including failed execution. Preparation and retirement share the same Free/Finish selection and resource release methods.

Native batch preparation resolves predicates, selects the execution stream and reserves completion storage before binding host tasks, KV tables, latent inputs and tensor outputs. Model callbacks supply numerical layouts and tensor views. Output writes are grouped by device and representation through the shared `TensorStore`; each accepted write and task belongs to its pending output before later reservations can fail. Media encoders consume the unit positions selected during reservation. Failed preparation uses the executor's shared resource retirement path, including partially reserved host work.

At commit, Rust writes unresolved completion predicates through `TensorStore` and checks tensor writes, latent trajectories, KV transfers, exports and pending request calls before making any store visible. The executor then applies the resource updates and device token state. A later failure is fatal because a successor may already observe committed resources. Earlier failures retire provisional outputs on the batch's stream, fence device readers and revoke transport registrations through the same storage owners used by normal retirement.

Native `PendingOutput` objects own each call's projected progress, capture spans, tensor exports, result decoding and output-row retirement. The independent Rust core initializes output generations from the call and checks score and KV output limits before resource commit. Tensor exports are assembled and retained as native values; the core checks output declarations and descriptor byte limits before accepting them. Batch delivery collects exports directly from successful pending outputs after all host callbacks finish. Sampling predicates, invalid distributions, speculative acceptance and canvas stopping resolve after readback. Failed and skipped calls report the request's accepted coordinates and cannot advance its progress. Speculative acceptance advances logical position, random-draw count and visible KV length together; rejected drafts remain initialized but invisible. The executor materializes every ready row before applying native request updates. Host callbacks may export deferred products or media, and run without borrowing the pending result or holding its mutex.

Each pending output retains its sampling rows, penalty bases, device lengths, positions and prompt logits in native state until commit. The executor installs verified lengths, advances decode rows together, applies explicit prefill or verification coordinates and copies prompt logits. `DecodeState` supplies the numerical tensor updates; device-computed lengths and positions stay on the device. The native binding releases the borrowed views after the updates are enqueued.

The executor assembles native `RequestOutput` and `BatchOutput` values, including failed calls and successful products, and the service sends them directly through IPC. Direct Python callers receive a result view when they consume the output. A recoverable numerical failure reports the matching request's accepted predecessor without advancing it; export failures remain fatal. Batch cleanup cancels unresolved calls only when no completed batch result exists, so consuming a successful or recoverable failed result leaves continuing requests available.

Each batch owns a native `BatchInputs` that retains tensor reads, latent and KV imports, image preparation tasks, storage dependencies and predicate readback. Its readiness check observes native resource state. A subscription captures the current dependencies and notifies once they are all consumable, including failed dependencies whose errors the consumer must observe. Closing inputs suppresses pending notifications, cancels queued preparation, abandons unadopted imports and releases readers through their existing owners. Every release is attempted even if another fails; physical storage remains retained until its device and transport accesses retire.

Rust selects completion-predicated calls and records their readback spans in batch order. Local reads are grouped by device; imported sources fill their reserved rows after joining transfer fences. All rows share one `OutputBuffer`, which is sealed after every copy is submitted and decoded only after its device events complete. Failed preparation fences acquired reads and abandons the buffer through the same storage owners. Canvas continuation stays in its device slot and does not enter host predicate readback. Python supplies tensor copies and consumes the resolved decisions without keeping capture or transfer lists.

The native backend resolves resident KV exports and collects storage dependencies from latent writes, KV writes, imports and recycled units. Supplied block tables override only their named groups; other groups use resident tables until the batch installs its assignments. Imports wait for these dependencies before numerical copies start. Read-credit exhaustion retains earlier imports and resumes at the refused import after capacity returns; the return sequence prevents a missed notification between refusal and subscription. Once imports are submitted, subsequent advances only capture pending predicates. Numerical callbacks run without borrowing the input set. During serving, a `Submission` sends its readiness notice and wakes the native rank channel directly; callbacks never execute the batch themselves.

Input admission selects consumers and destinations from the native batch plan. Tensor and latent imports share transport selection and read-capacity admission. Video encoders borrow local shared-memory inputs, and muxers consume encoded row prefixes without copying unused capacity. IPC admission checks source metadata and input roles once; the receiving latent pool checks its physical element layout. Python supplies placement and tensor views through the existing numerical backend, while Rust retains reservations and advances preparation.

Native `BatchState` binds active latent inputs against the request's committed solver step or its imported trajectory step. It checks all intervals before assigning writable image views and binds their page tables together through `LatentPool`. The existing image and media builders supply model dimensions and fixed-slot page mappings; Python retains the numerical views used by the runners. Predicated calls receive no writable view and do not advance their trajectories.

Each native batch retains the request epochs, freed buffers, retained exports and device fences needed to retire its commands. `Finish` revokes unretained exports and cancels imports; `Free` takes precedence over retention. A result acknowledges these commands only after the request, tensor, latent and KV owners report that their readers have retired. Export selection and revocation share one native implementation across these stores. Request-slot resets are then issued before acknowledgment on the device's current stream; later batch streams wait for it before reuse. Retirement does not wait for those resets to complete, which would delay acknowledgment behind later queued work. Abandoning a batch defers its outstanding fences while retaining its numerical resources.

Native `Call` objects hold computation kinds, numerical parameters, tensor dependencies and resource limits. Serving and direct Python submission use the same native validation and dataflow methods. Python reads immutable numerical views that are created once on demand. `RequestKey`, `CallId` and `BufferId` expose the request epoch, scheduler call ordinal and buffer generation directly to execution and storage, with value equality and hashing across IPC and process messages.

Native `Batch` owns submitted calls, request commands and resource assignments. IPC receipt and direct submission share that description with the executor; Python materializes only the numerical views it reads. Explicit construction, `replace` and mapping decoding use the same native checks for call membership, buffer spans, KV assignments and media ranges. The executor processes request commands from the native batch and supplies admission parameters to the numerical request state. Python callers use `Batch.replace` to derive another submission and `to_mapping` or `from_mapping` for explicit serialization.

Canvas sampling parameters use the same native FP32 values in deployment configuration and admitted requests. Exact comparison therefore tests the sampling values used by execution, including after IPC serialization.

Forward rows retain their original call indexes across context segments, guidance branches and canvases. Missing guidance prefixes execute before their denoiser rows; branches sharing a physical prefix submit one prefill. Rust retains tokenized prefixes for the image request and refreshes branch KV coordinates for each submitted interval. Context results commit after every segment returns. Captured greedy rows and eager sampling share result capture and token submission. `OutputBuffer` copies shared sampling and score columns once and binds each pending result to its own span.

Rust prepares inline image inputs on the shared host lane and retains their tasks in `BatchInputs`. Resident image reads use the tensor store's stream dependencies. The executor commits encoder features with their spatial metadata, gathers final latent banks for image decoding, and writes optional resident image outputs. Text, vision and video/audio condition encoding use the same retained input and tensor export paths. Python supplies image transforms, numerical rows and encoder calls.

Rust assigns prompt scores to their original runs, carries the last logits across text and vision segments, and records speculative base coordinates while selected extents remain device tensors. Canvas rows share one completion copy; their stop outcomes feed device continuation writes without host readback. For token and canvas results, Python supplies numerical score packing and tensor operations without mutating request progress or output spans.

Token `SamplingParams` shares the engine's native FP32 representation and numerical validation across Python calls, admission and IPC. Native `SamplingMetadata` resolves allowed and forced tokens, branch stop tokens, speculative prefixes and semantic Philox draws. The sampler groups compatible rows by device, vocabulary and numerical selector, then restores call order after the numerical backend returns. Captured greedy selections follow the same native parameter and terminal policy; calls requiring richer controls sample their retained logits. Python prepares penalty-count views and device columns and executes the greedy, top-k or categorical selection, including predicates and speculative acceptance. Penalty preparation leaves committed counts unchanged until execution commits the accepted result.

Native `ModelExecutor` binds component operations to numerical runners, assembles compatible rows in first-appearance order and executes each group when its consumer requests the next result. Numerical input type, spatial shape and attention causality determine grouping; interdependent text and vision context segments remain together with per-row causality. Earlier invocations retain their outputs when a later invocation will reuse the same runner's buffers. Rust partitions whole rows for microbatches, preserving independent KV writes and empty participants in expert communication. Python packs those partitions and executes the numerical backend, including its graph replay and output checks.

Input binding selects each lane's operations, physical row capacity, numerical context and capture sizes in Rust. Capacity planning and allocation share the same prefill and decode selection. Text and canvas runners on one stream share graph intermediates; independent streams and expert microbatches retain separate pools. Persistent inputs are allocated before capture, and failed construction closes the backing and context already acquired. Python supplies buffer layouts, tensor allocation and numerical context preparation.

Expert binding discovers the model's routed layers once and gives every microbatch its own exchange at the same capacity. With attention and expert workers on separate ranks, the source broadcasts its actual numerical token bound, including padding and multimodal inputs, before collective workspace allocation. Execution-lane limits and capture-device selection remain with the native runner owner.

The same native owner selects eager execution or resident graphs, orchestrates startup capture and runs standalone modules. Prepared numerical backends supply graph keys and input views; replay uses the expert step's shared transfer capacity, while Rust accounts for real and padded tokens. A configured bucket missing after startup fails before a forward; a standalone signature without a resident graph runs eagerly. Expert steps include empty microbatches, and every host turn and stream joins before their results are combined. Module invocation and capture restore the caller's stream ordering on exceptional exits too. PyTorch retains graph executables and numerical capture/replay operations, including its graph RNG handling.

Native `ModelExecutor` owns the loaded model, component bindings, execution configuration, numerical runners, streams and graph storage for one rank. Worker startup and request execution use this owner directly. It discovers numerical methods once, selects encoder capacities and output placement, binds request storage, and orders warmup, capture and retirement. Python supplies tensor preparation, numerical model contexts and media reconstruction helpers.

`ModelExecutor` also owns locally bound module methods and their prepared contexts. Contexts prepared during startup remain resident and share one stream, scratch owner and graph pool per method. Serving prepares unseen numerical sizes eagerly and retains at most the request-pool capacity per method, retiring the least recently used context after its stream drains. A graph failure retires its context before propagating the error. Module streams close in reverse creation order after their contexts; the shared scratch outlives every context that borrows it. Python supplies numerical sizes, tensors and context preparation without maintaining a second module cache.

The same native owner creates execution lanes, forks streams for modules and expert microbatches, and retains the input-copy stream. Lanes use the configured SM partitions; a module forks the unique lane covering its operations on its device. Input preparation overlaps reserved copies with computation on the caller's stream, then joins through reusable CUDA events, including after a copy or computation error. This join does not wait on the host. Normal shutdown drains execution, destroys graphs and contexts, and closes dependent streams before their parent lanes. Aborted shutdown retains backing until process exit without waiting for CUDA work or collective retirement.

Native `ExecutionOutput` retains row-aligned tensor views, vocabulary shards, optional layouts and the producer's completion event. Its `clone` and `materialize` operations join that event before invoking PyTorch copies or vocabulary gathers. Combining microbatches concatenates their row views after the caller joins their streams; outputs retained across graph replay require a copy. Greedy output concatenation remains a numerical backend operation.

`ForwardStats` is an immutable view of the native counters shared by numerical results and IPC. `BatchState.record_forward` accumulates each completed invocation directly in Rust, and `execution_stats` adds the batch's component timings to an independent snapshot. The executor consumes the native counters without constructing a Python dictionary. Explicit Python serialization uses `to_mapping` and `from_mapping`.

`ModelExecutor.forward` and direct homogeneous calls through `ModelExecutor.run_batch` share the native invocation path. Rust orders input copies after the control stream, records device completion and joins submitted work before reporting preparation or execution failure. These dependencies use stream events without waiting for device completion on the host. Forward iteration exposes each group's row indexes and outcome; a consumer stopping on an error starts no later group, and fatal errors terminate iteration immediately. Rust records invocation times and call counts, while the numerical backend supplies token counts and graph observations. The binding currently consumes Python numerical objects through PyO3.

The worker's native `RequestPool` binds each admitted request epoch to the engine-assigned slot. It tracks pending calls, accepts progress without allowing late results to roll it back, and rejects stale epochs after slot reuse. A `Request` owns immutable admission parameters and native progress values; result observers can retain its epoch after the slot is reused. Requests retain borrowed diffusion tensors and buffers; the executor drains device readers and the request pool drains host writers before slot reuse. Direct Python callers and serving share the same request implementation. The request core is independent of Python and is also used by the TVM-FFI experiment.

`RequestProgress` is an immutable native snapshot. The native executor advances projected token positions, sampling counters and KV extents directly; mathematical position layouts may supply an absolute position. Diffusion progress follows the same validated `LatentUpdate` that commits its physical trajectory, and release resets the solver step. Imported trajectories bind their initial step before execution. `BlockTables` resolves the visible KV prefix against every installed group and its common capacity in Rust. Python neither reconstructs progress records nor builds group views to perform that query.

The native `EventPool` shares CUDA events across tensor storage, KV transfers and output buffers. It owns lease references, producer-stream assignments, reusable events and deferred storage owners. An early final release fails without consuming its reference; deferred release waits for device completion and invokes callbacks after unlocking. Closing stops new work, drains recorded events and notification streams outside the pool lock and Python GIL, then releases retained owners. Cyclic garbage collection uses the same shutdown and keeps the pool closed so later ticket destruction can return its references safely. Event objects that callers still hold remain available for observation and are not reused by another lease.

Native `GraphStorage` retains the PyTorch allocation pools shared by numerical executions and accounts for their combined device budget. During startup, a bound budget includes process growth outside the pools, such as graph executables and communication resources; sealing switches accounting to the pools alone. Shared pools are charged once and remain owned until their last execution releases them. Executions sharing a pool must serialize replay and allocate persistent inputs before capture. Numerical owners drain their graphs and borrowed views before releasing pools. The Python backend supplies allocation scopes and memory measurements; replay performs no residency inspection.

Each numerical runner composes a native `Execution` that owns its prepared context, graph buckets, pools and microbatch rotation. Text, canvas, diffusion and packed vision variants use native `GraphBucket`; variants are indexed by expert transfer capacity, with `None` for independent calls. Expert layer participation is recorded directly between native owners. After external readers drain, closing retires graphs, host turns and the numerical context before releasing its pools. Cleanup attempts every release and preserves the first error. Diffusion's constants and request-state views belong to `DenoisingBuffers`; graph lifetime has no separate solver-specific subclass. PyTorch still supplies numerical contexts, graph executables and tensor operations.

Native `CUDAGraph` owns capture segments, retained inputs and outputs, replay order and closure for both direct library calls and worker execution. Each graph has a private capture stream; computation uses its context's stream. Weight prefetch splits a call into ordered graph segments sharing an allocator pool, with external events preserving dependencies across the intervening copies. `CUDAGraphRunner` adds numerical warmup, state restoration and fixed input tensor correspondence. Python supplies PyTree tensor copies and PyTorch capture preparation. Replay uses PyTorch's executable API to preserve captured random-generator state. It still crosses the Python binding and is not a GIL-free launch path. Callers drain final readers before normal close; aborted or unfinished final-owner disposal retains backing until process exit.

Direct graph callers warm every kernel specialization before capture. A capture invokes the numerical call once and runs its optional restoration after the attempt, including on failure. Cross-device calls supply a `torch.cuda.MemPool` for every additional allocation device, constructing each pool with that device current and retaining it through all borrowing graphs and tensors. Replay returns retained output views that the next replay overwrites; callers order final readers before replay or storage reuse.

Each text runner owns native `TextShapes` for its decode and prefill captures. Rust builds prefill buckets within the KV pool's capacity and selects a serving bucket by query lengths, causality, embedding replacement and requested outputs. `ModelExecutor` prepares token, canvas and image calls at startup, borrowing scratch KV pages and latent views from idle pools. Prefill capture fits real rows within hybrid page costs and each request's token limit; unused capacity becomes padding. Decode first computes its scratch prefixes and restores live predicates after capture. Image denoising computes each guidance prefix before its dependent forward. Numerical calls share stream ordering on successful and exceptional returns, and scratch storage drains before reuse. Python constructs numerical inputs and evaluates models through the same buffers and methods used during serving.

Prefill reserves one extra padding row; decode uses the configured row order and never borrows a prefill bucket. Calls that only write KV prefer a cache-only graph when one is configured. Missing required shapes fail before numerical execution. Python supplies host metadata and fixed tensor views and pads the selected shape; the model executor keeps no duplicate bucket tables. Capture shapes remain immutable when exchanged between expert peers.

For packed vision, native `Execution` captures every image count up to the smaller of the admitted batch size and 16. Captures run largest first and share pixel backing and an allocation pool. Serving splits larger batches into groups, selects the exact graph for each group and retains its feature views before the next replay reuses captured output storage. Numerical helpers copy patch rows and grid metadata and return only each image's valid features. Packed vision uses the same graph buckets, storage budget and retirement as token and canvas execution.

The native `HostBuffers` ring owns host inputs used by block tables, latent page indices, encoders and model input buffers. Python allocates and fills the tensors; CUDA copy sources use pinned host memory. Rust selects slots round-robin and records a native event after each asynchronous copy. Reusing a slot waits only for that slot's previous copy. Closing drains copies before releasing host allocations. Device waits release the Python GIL, and completed copies do not wait for unrelated streams. Production and the TVM-FFI experiment share this owner.

The native `OutputPool` bounds host readback allocations for sampling columns, predicates and image bytes. Each batch has a distinct `OutputBuffer`; only its host storage is reused. Integer columns grow from the allocation's head and byte captures from its tail. Sealing records a fence on every declared producer device. Device completion resolves the batch's storage fence independently of result consumption; reuse also waits for every result row and retained CPU reader. CUDA timing events remain readable through observation. Python supplies allocation and tensor copies. Rust snapshots completed integer columns once per batch and decodes each packed logprob column once, preserving selected, top and requested-token ordering with competition ranks and token deduplication. Sampling, candidate scores and predicates consume these native values directly. Host copying and score decoding release the GIL; their cached values remain readable after the pinned allocation is recycled.

The native `KVCacheManager` owns resident transfer descriptions, each destination's sent and installed extents, and physical accesses to cache units. Incremental transfers extend the current destination prefix in batch order; the complete update is checked before any resource owner commits. Releasing a consumed descriptor preserves the destination prefix for subsequent transfers and leaves physical exports to retire through their readers. Request retirement clears that request's descriptions and transfer bases. Python owns numerical page views and representation conversion.

KV export and installation execute directly in the native batch executor. The cache manager selects each group's incremental or sliding-window suffix and reserves its source intervals before asking the numerical backend for page views. Failed exports revoke every accepted locator and release their source reservation. Installation adopts the completed import and updates the numerical verified length. Pending exports and installations remain native through batch commit and IPC delivery; direct Python library calls use the same implementation and receive a Python transfer description on return. All active calls, including native transfers, register their producer devices with the output buffer before execution.

Native `BatchState` binds KV storage for active calls, including alternative-prefix rows. It installs scheduler assignments through `BlockTables`, recycles units that imports have not initialized, and retains each call's read and write intervals until output completion. `BlockTables` checks the backing pool's unit bounds before copying or committing any assignment, including direct installations. Forward-row indices are native batch metadata shared by token, canvas and diffusion consumers. Python supplies the numerical table-copy and cache-reset operations.

KV imports begin after conflicting storage accesses retire and tensor inputs obtain transfer capacity. The native executor selects destinations from its request pool and scheduler-assigned tables, retains resident descriptions by shared reference, and records each accepted import in `BatchInputs`. Temporary read-capacity exhaustion defers preparation and keeps accepted tensor reads. Other preparation failures abandon all accepted inputs; their physical accesses continue to retain storage until completion. Diffusion conditioning reads already installed exports from the cache manager.

After numerical views and output reservations are bound, native `BatchState.complete_inputs` accepts prepared inputs for active calls. It checks KV imports against current resident exports before exposing tensors, then delegates producer-fence ordering and visibility to `TensorStore` and `LatentPool`. Borrowed media remains with its existing owner. Input roles, placement and immutable transfer dimensions were established during admission. A latent import advances provisional progress to its transferred step. Failure after numerical execution releases imported pages using each `LatentImport`'s adoption state. Batch and input borrows end before completion callbacks run.

The native `KVImporter` resolves destination intervals through `BlockTables`, reserves them through the cache manager and runs copies on the shared host-lane implementation. Incremental imports preserve the physical pages that hold their accepted prefix; only newly assigned units may reset. Rust selects direct copies when source bytes and scales can be installed unchanged, otherwise advances page spans through the existing conversion workspace. It selects layer, head and scale regions from native transfer descriptions, retains started reads and retires numerical consumption before reusing the workspace. Native and Python callers share region coverage and read-capacity handling; selected locators retain native metadata through physical transport calls. Python constructs borrowed views and performs quantization conversion through the numerical cache library.

A `KVImport` owns its native transfer description and destination tables. Adoption checks that the accepted prefix and installed tables still match. Conversion workspaces and CUDA streams remain owned until reads and device writes drain. Cancelling an import revokes consumption and wakes workspace waiters. Task completion also retires cancelled work that never entered its numerical action. Shutdown stops imports before transports and requires all destination accesses to retire before closing cache storage.

The shared CUDA module supplies event queries, host waits, consumer-stream ordering, elapsed time and IPC event handles to production and TVM-FFI execution. Events allocate in the producer stream's context when first recorded. Output events from owned SM partitions retain their Green Context; callers retain the contexts of externally supplied streams. IPC imports retain their primary context, and native device guards select and restore the calling thread's context. A separate notification stream per producer prevents a stalled producer from blocking independent completion. `StreamSignal` retains its selector descriptor through the scheduled host function, and channel notifications wake the worker directly. These callbacks perform only native notification work.

The native `CUDAStream` owns execution streams, Green Context SM partitions and bounded ingress/output event rings. Partition allocation uses one disjoint split tree and rejects SM counts the driver cannot allocate exactly. Forks share their parent's SM partition and retain it independently. `wait(producer)` and `record()` enqueue device dependencies; consumers join the returned output event before its ring slot is reused. Independent lanes can submit before those joins. Graph capture and NCCL transfer streams use the same native creation and retirement mechanism. Each stream exposes its retained PyTorch view to numerical code. Close execution contexts and graphs before their stream; normal stream closure retires bound communication and drains GPU work outside the Python GIL. Aborted closure retains resources until process exit.

Native `StreamCommunication` owns the stream's NCCL communicators, reusable gather buffers and registered peer windows. Contexts and graphs borrow these resources across preparation changes. Rust submits collectives through NCCL's C API outside the Python GIL; Python supplies process-group bootstrap and numerical tensor views. Asynchronous collectives use a transfer stream in the same SM partition and join consumers through device events. Uneven exchanges compute row offsets directly and group peer sends and receives. Gather buffers remain ordinary transport storage; only explicitly owned symmetric windows are registered. Normal close retires communicators before releasing window backing, while failed retirement retains their allocations until process exit.

The native `HostLane` supplies bounded threads for image preparation, media encoding, transport reads, KV import copies and diffusion input preparation. Idle threads take work from one shared queue. Capacity is reserved before inputs exist. A `HostTask` carries its action, result and input lease; deferred actions submit once their inputs are CPU-readable. Dependencies, results and physical completion share native waits, which release the Python GIL. Numerical callbacks retain ordinary Python and PyTorch code. Media tasks use the same queue, cancellation and input retirement directly: image tasks wait for their output-buffer copy and retain its CPU reader through encoding or cancelled-copy retirement; video tasks release their shared-memory borrow after encoding; audio and mux tasks retain the request container. Native pending outputs commit deferred media tensors after all tasks succeed, exporting only initialized encoded row prefixes. Media reading uses this same deferred output path.

Image encoders and the video muxer return completed bytes. Native `PendingOutput` publishes those bytes through `MediaSource`, the same POSIX storage owner used for condition media at the frontend. Export reserves physical space and copies outside the Python GIL. Pending results retain their segments until delivery; `BatchResult` carries that ownership through execution cleanup and IPC response serialization. A successful send or direct Python result conversion hands the name to its receiver. Failure, abandonment or destruction before handoff unlinks it. The engine claims a delivered segment with `SharedMedia::open`, which unlinks its name while retaining the readable mapping. Python retains codec and packet operations. The native request owns its mux container, and host tasks retain that container until their operations finish. Removing a request releases its reference without closing a container underneath an active codec.

Numerical `Microbatches` use one fixed host-lane thread per CUDA context to retain warmed CUDA library handles. Rust rotates ordinary model calls at expert dispatch yields and removes completed calls from the rotation. A failed call wakes its suspended peers; every host task retires before the original error returns or the owner accepts another invocation. Python activates the numerical contexts and enqueues CUDA stream fork/join dependencies. Captured replay executes those device dependencies without running the host rotation again.

Cancelling an unsubmitted or queued host task returns its capacity. Queued cancellation removes the action under the same lock used by threads to claim work, so it cannot race with execution or accumulate unused inputs behind a stalled task. Running actions finish normally. Input leases release only after the producer completes successfully; failed or cancelled producers cannot establish safe reuse. Result callbacks run outside native locks after capacity returns. Closing cancels unsubmitted tasks before joining workers, so submitted dependents can finish; abort stops admission without waiting for potentially stalled device work.

The native `BufferPool` backs scheduler-placed products with fixed device arenas. Its Python-independent core assigns nonoverlapping ranges and accepts release only for the current binding issued by that pool. Ranks that hold a subset of the logical products can use compact physical placement. The numerical backend creates tensor views while the owner holds the pool lock and returns the binding if view creation fails. Views retain the arena backing; storage owners must retire device accesses and transport readers before releasing a binding for reuse.

The native `TensorStore` owns values that pass between calls. Its Python-independent core owns capacity, relay lanes, batch commits, read leases, shared imports and physical retirement. A `Buffer` becomes readable after production and result commit; CUDA consumers wait on its producer fence. A `TensorRead` retains the acquired tensor view through consumer completion; logical release rejects new readers but preserves existing reads. Physical reuse waits for local readers, successful native transfer and export completion, and producer and consumer CUDA events. Reclamation queries native completion without entering Python or synchronizing unrelated streams. The numerical backend retains tensor views, copies values and submits transport reads; it keeps no second buffer lifecycle.

An import shares resident coverage and fetches only missing regions into the reserved destination. Readers of an earlier shard keep that view while `TensorImport` coordinates the transfers needed by full-tensor consumers. Failed or cancelled imports retain their destinations until physical transfer completion. Request relays use bounded scalar lanes with fixed addresses; the store admits another call into a lane only after every value in that lane retires.

The native `LatentPool` owns diffusion trajectories in two fixed page banks. Its Python-independent core selects workspace ranges, tracks page ownership, validates batch updates, and retires imports and exports through the shared native `Completion`. Preparation writes the inactive bank; applying a `LatentUpdate` advances the committed generation and switches banks. Imports reserve their destination pages before transfer and become visible after producer fences are ordered on the consuming stream. Exported bank versions remain immutable until every reader retires, including versions exported before the first trajectory commit. Cancellation retains occupied pages through physical completion. Python supplies allocation, tensor views, gather and scatter operations over this backing, with no duplicate trajectory or transfer-lifetime state.

`LatentPool.bind` creates native `LatentBuffer` views containing device page indices and contiguous, padded latent values. Page order and workspace offsets remain native; Python supplies the bulk page-index copy and numerical gather/scatter operations. Callers retain these views through numerical completion and include live views in `occupied` when binding another call. Image denoising uses the pool's step workspace; standalone denoisers supply their own runner buffers and construct the pool with `with_workspace=False`. Capacity planning uses the same option when accounting for storage.

After submitting latent writes or reads, the native executor records their completion in `BatchState`. Rust derives the trajectory update from that call's native plan and keeps it in `PendingOutput` until batch commit. This notification requires no device wait; stream dependencies and completion events still govern physical access and reuse. Transferred image trajectories use explicit generations; standalone media versions its slot-local trajectory by accepted step. A rank that does not execute the numerical consumer leaves no update. The executor validates the prepared updates together, applies the pool changes and advances request progress. Python retains borrowed numerical views on the pending output.

The native executor exports completed latent writes from the component's output rank when a non-local transport is configured. A latent transfer call exports the committed bank without advancing its generation or step. Both paths reserve pages through `LatentPool` and use the shared export operation, retaining retirement signals directly in the native pool. Transfer descriptions remain native through result delivery; physical backends supply locators. Every accepted locator belongs to its pending output before result conversion, so a failed batch can revoke it. Final denoising releases its bound guidance-prefix slots only after latent exports succeed, preserving the accepted trajectory and prefixes when export capacity is refused.

Direct pool callers construct immutable `LatentUpdate` values with their trajectory parameters. `validate_updates` checks the whole batch before `apply_updates` makes any trajectory visible; both methods consume the stored native values.

Rust plans each tensor fetch from bound source locations, preferring process-local replicas and preserving export order among other sources. Requested regions split into disjoint reads using the same region subtraction as the engine's coverage query. The numerical backend validates the complete destination and forms borrowed views before submission. Missing coverage or read-credit backpressure leaves the destination untouched. A backend or observer failure cancels all submitted reads, preserving the original error while tickets retain any outstanding physical access.

Transport backends share a native `TransferCapacity` for bytes and read credits. A `ReadReservation` takes an entire fetch's credits before any read starts, hands them to individual reads, and returns unused credits on close or destruction. Budget accounting and reservation lifetime run independently of Python. A refused fetch records the credit-return sequence; registering a notification after an intervening return wakes it immediately. Notifications run after unlocking, so a consumer can retry admission from its callback.

KV, latent and tensor owners share the native `export_tensor` operation. It selects configured backends by the tensor's device, requested host representation and reachable consumers, then gives each retirement signal to the storage owner. A CUDA payload that cannot fit its VMM pool is sent through the available host mechanisms. Failure revokes the accepted locations before propagating the error; their outstanding device accesses and readers still govern physical retirement. Native callers select, export, read and release through `Transport` directly. Python supplies tensor views, payload packing and numerical copies.

`Transport` owns each endpoint's physical backend and shared read pool. Local, shared-memory and CUDA VMM exports reserve bytes before allocating backing or recording producer events, then transfer ownership to the common buffer registry. Channel exports return independent bytes and release their temporary reservation immediately. CUDA exports retain original source views through pool copies, own direct POSIX descriptors and use the existing per-device VMM pools. Cross-host readiness waits on the source device's stream outside the GIL. An incomplete registry shutdown retains its VMM backing and descriptor service for accepted readers. Failed preparation returns unused capacity; an unresolved device drain retains its views and allocation through process teardown.

CUDA POSIX allocation handles reach local consumers through native `DescriptorGrants`. Its Unix datagram service uses Linux abstract addresses in the workers' network namespace, with no shared filesystem directory. Registration retains an owned descriptor; revocation refuses later requests, while in-flight replies and received descriptors keep their allocation reference. Received descriptors are closed on exec and belong to the importing caller. Closing or dropping the service revokes registrations, wakes its native thread and joins it before returning. Python neither serves grant requests nor keeps a descriptor table. Fabric handles continue to be imported directly.

The native `TransferPool` owns read admission, tasks, cancellation, failure propagation and credit returns through the common Rust `HostLane`. It also owns one copy stream per transport thread and device. `ReadBackend` supplies numerical reads and language-specific observers; task control and completion do not pass through Python task wrappers. Submission reserves credits before recording a destination handoff event; failed preparation cancels the reservation. The copy waits for this event and producer readiness, without waiting for later work on the submitting stream. Its `TransferTicket` exposes consumable views before physical completion, so consumers can enqueue work behind the read fence. Cancelling a queued read returns its unused credits immediately; an executing read returns them only after device access drains. Borrowed local views retain their source grant through every consumer stream. A failure to establish physical completion keeps the affected resources and credits occupied through process teardown and surfaces through the pool and storage owners.

Physical tensor locations are immutable native `Locator` objects shared by transport owners, registry grants and read execution. Tensor and latent exporters use those descriptions directly when constructing IPC results. Python numerical code accesses field views; standalone Python IPC records use `to_mapping` and `from_mapping`. Explicit Python construction and mapping decoding share the IPC crate's descriptor validation.

Channel reads enter the same native pool before allocating payload or destination tensors. Rust retains the locator through queued execution and cancellation; channel and shared-memory reads share destination preparation, region selection and copy submission. Unindexed CUDA devices resolve on the submitting thread before work reaches a read thread. Python allocates the private host tensor, pinned for device DMA, and exposes its writable buffer. Rust copies directly between that buffer and the native channel payload; export packing likewise exposes its host buffer without a Python bytes intermediate. Supplied destinations are checked before admission, while allocation and shape errors without a supplied destination fail the returned ticket. Channel export, payload preparation and transfer work use the shared profiler ranges.

`TransferTicket` keeps result readiness, cancellation, borrowed-view closure and physical retirement in the independent worker core. It owns the readiness and handoff events, records borrowed consumers, and uses the shared native `EventPool` to fence their final access. A late device failure prevents further consumption even if a view was previously exposed; its existing consumers still retain that view. Physical retirement uses the shared native `Completion`, and its observers can outlive the ticket while consumer fences finish. Python supplies tensor copies, selects computational consumer streams, and records tensor use with the PyTorch allocator. CUDA event operations and transport stream ownership run natively.

Local reads acquire their producer registry directly in Rust. Borrowing and copying share read-credit admission; copied inputs release their source before the read's physical retirement, including queued cancellation. Borrowed reads retain native ownership after their Python ticket is dropped, and the consumer pool drains outstanding borrowed access through the producer's event pool at shutdown. Native condition variables serve host callers waiting for readable values. Python supplies tensor views, while source release, credit return and consumer-event completion use native operations.

Local and same-process CUDA VMM reads find their source through a shared native weak registry. Closing or destroying a producer removes its endpoint from lookup; existing read grants retain the native registry until physical access ends. Readers retain source storage without retaining Python transport objects.

Shared-memory reads use the same native task admission and copy streams. Rust opens and claims the source mapping, waits for readiness with native cancellation, and acknowledges it after a synchronous copy into private host storage. Python supplies that numerical copy and borrowed tensor views. A CUDA destination uses pinned host storage retained through DMA; the source mapping can retire independently. Preparation failure returns both the source claim and the read's capacity, while failures of device completion retain the in-flight storage.

CUDA VMM reads also use the native transfer pool. Rust selects local borrowing or remote import, owns received descriptors through mapping, imports producer fences, and orders reader claims, copies and acknowledgments. Peer accessibility determines which device can map the source. A copy across devices without peer access finishes the source-device fence and acknowledgment writes on that device; those waits release the GIL. Failed acknowledgment completion retains the mapping and stream with the read. Python supplies the existing CUDA accessibility query, mapping primitive and tensor views.

Local, shared-memory and CUDA VMM transports retain their source buffers in the native `BufferRegistry`. Its Python-independent core owns bounded registration, read grants, revocation and reclamation. Releasing a buffer revokes further reads; its retirement waits for producer completion, outstanding readers and backend acknowledgments. Backend queries run under the owner's lock to keep mapped words alive; physical reclamation and completion observers run after unlocking. Only successful native completion removes a reclaimed source. Unknown producer completion and failed reclamation keep their backing retained, while independent buffers continue to retire. CUDA VMM separates the original source from its exported pool chunk: the source retires after its copy finishes, while remote acknowledgment words govern chunk reuse.

A native `TransportBuffer` retains each export's numerical views, producer event, backing and byte reservation. Event retirement returns capacity and releases direct descriptor grants in Rust. Shared-memory retirement closes the mapping on the native host executor when CUDA unregistration may wait. All three backends use the same retirement completion; Python callbacks observe completion but do not reclaim transport backing. Python supplies tensor copies and numerical views.

Native `VmmPool` owns chunk placement and remote-reader retirement within an exported device allocation. Retirement orders its private copy stream after the producer and retains the chunk and descriptor grant. Reaping submits batched header copies into reusable pinned storage, then observes them on a later completed poll. The pinned cache grows geometrically and frees its allocations only at close, because freeing pinned memory can wait for unrelated GPU work. Reaping does not wait for the caller's CUDA stream or materialize acknowledgment tensors in Python. Only named readers retain a retired chunk; an unclaimed slot needs no acknowledgment. Closing requires all external accesses to end, then drains header initialization and readback before releasing the mapping. Python supplies exportable backing and numerical tensor views.

Shared-memory tensor exports use native `SharedBuffer` storage, backed by the same POSIX allocator as media. Python copies tensor spans into the borrowed mapping; a CUDA export registers those pages for DMA and marks them ready in a native stream callback. The callback writes only the readiness word and never enters Python or calls CUDA. The existing worker notification wakes the execution loop to reap completed exports. Reaping checks readiness and reader acknowledgments before returning storage. CUDA host unregistration can wait on unrelated device work, so a native `HostLane` performs that blocking retirement outside the execution loop. Shutdown drains pending copies and joins retirement work; a partially submitted copy without a recorded event requires draining its stream. Borrowed Python tensor views retain the mapping after unlinking, while page-lock ownership ends with producer retirement.

Native `SharedRead` owns a consumer's mapping and acknowledgment slot. It waits for readiness outside the interpreter and observes the transfer ticket's native cancellation state. Failure, timeout or destruction returns the acknowledgment. Python and NumPy borrow only the selected payload range; those views retain the reader until their final release. Tensor transfers copy that range once into private host storage, pinned for a CUDA destination, and acknowledge before submitting the device copy. Media encoders read the existing mapping directly. Condition codecs open POSIX descriptors through the same allocator; video decoding uses FFmpeg's seekable `fd:` input without depending on a shared-memory mount path.

## Token and canvas calls

Prefill, token decode and token denoising use separate homogeneous numerical calls. A prefill can write context without projecting logits or sampling. Readout canvases attend to that context without changing its KV entries; their candidate probabilities are normalized over the full vocabulary.

Rust prepares token and canvas inputs from the native batch descriptors. It selects logits, device continuations and request coordinates, partitions readout candidates, and retains visual feature reads through the shared tensor store. Python constructs numerical rows from those tensors and scalar coordinates; visual builders compute framing and M-RoPE positions without reading request state. A predicated verifier concatenates its device token and draft tokens on device. Indexed decode borrows tokens and positions directly from its request slot.

Block-diffusion generation retains each request's canvas tokens, stopping history and self-conditioning embeddings in its request slot. Each scheduled denoising call advances one step. A completed block publishes its tokens together, and a causal prefill commits those tokens to context before the next block starts. EOS, token limits and stop strings apply to the delivered prefix of the block.

The engine may queue a successor before its predecessor completes. Device continuation predicates make successors of a stopped canvas no-ops. The native request pool tracks submitted block and step coordinates independently of accepted device results, and rejects skipped or repeated steps before execution. New request epochs start with no submitted canvas. Completion is accepted only for the current request epoch and submitted call. Cancellation retains request resources until outstanding readers retire; only then can another request reuse the slot.

## Prepared execution

`ExecutionContext` owns numerical bindings and workspace lifetimes in Rust, for both direct Python calls and serving. `prepare` replaces its capacity and prepares attention, matrix multiplication, MoE and VSA call sites. Python supplies tensor operations and backend plans. A failed preparation releases partial bindings and views; the context can be prepared again. Stream communicators and registered windows belong to the borrowed stream and survive context replacement.

`TensorBuffers` retains contiguous tensor backing and symmetric peer mappings. Its numerical views are compact prefixes at the requested shape, rather than strided rectangular crops. `Scratch` shares transient buffers by operator role between calls serialized on one stream. Capacity growth happens outside capture and retains earlier backing for existing graphs. Explicitly supplied buffers and scratch remain caller-owned; close them after all borrowing contexts and graphs retire. Without supplied scratch, a context owns and releases its private scratch.

Activation installs call-site bindings, transfer scopes and the borrowed stream for an ordinary model call, and restores the enclosing bindings afterwards. Attention planning derives missing host lengths only when `derive_host_lengths=True`; serving supplies the mirrors and disables that synchronizing copy. Graph replay can use device lengths without rebuilding a host launch plan when its backend supports that execution mode. Retirement queries outstanding streams without waiting; an aborted context retains its resources until process exit.

For a numerical module placed on another device, native `DeviceTransfers` owns placement bindings, delivery streams and nested call frames. Scoped PyTorch hooks select the active context when modules are shared by nested or concurrent callers. CUDA event dependencies order inputs after their producer and rejoin the caller after output copies, including failed forwards. Eager warmup creates destination streams before graph capture; later captures reuse that context's destination streams while retaining their own origin. Python copies tensors inside numerical dataclasses and containers and writes caller-supplied output storage. CPU consumers use completed copies; CUDA consumers use stream ordering. Graphs and readers retire before preparation replaces those streams.

Startup prepares bounded input storage and captures the configured prefill, decode, canvas and image-denoising shapes. Each call copies its inputs into the retained buffers and selects a graph that holds its rows. Padding carries no request progress. Once prefill, decode or canvas graph preparation is sealed, a call outside its captured capacity is rejected. Graphs, buffers and captured numerical plans are owned by their execution context.

Canvas generation captures the numerical pass, vocabulary projection, sampler and state commit together. Readout graphs evaluate the shared canvas prefix and gather only the answer positions for the final projection. A readout tail that exchanges tokens with expert peers executes once at the agreed exchange capacity, keeping all peers on the same collective sequence.

The worker logs `uniserve-kernel-table` JSON after startup and when serving resolves additional call sites. Each record names the computation, layer paths, representation and selected provider. These records describe the executed configuration; they are not performance measurements.

The [execution profiler and sanitizer](profiling.md) correlate native batch stages with numerical ranges, CUDA calls and transfers. Their offline hints identify possible host waits and device roundtrips for investigation without changing serving behavior.

The scheduler's allocator does not advise its heap for transparent huge pages. Worker launches default `MIMALLOC_ALLOW_THP` to `0` and propagate an explicit operator value to local and remote ranks. This keeps automatic heap collapse outside the default serving allocation policy while preserving operator control of worker allocation.

## Replicas and experts

`--data-parallel-size` starts independent replicas, each with its own scheduler, request storage and KV pool. `--worker-ranks` gives the tensor-parallel rank count per replica when placement is not supplied with `--workers`. Requests go to a live replica with the fewest in-flight requests; ties rotate. Cancellation remains routed to the replica that accepted the request.

`--expert-parallel` partitions routed experts across one-rank replicas. `--expert-exchange` selects `alltoall`, `megamoe` or `dwdp`; the available representations and resource requirements follow the [expert providers](experts.md). Collective expert execution agrees capacities and layer participation across replicas, including replicas without local request rows. DWDP accesses distributed weights while retaining independent request progress.

Prefix caching is enabled by default. `--disable-prefix-cache` disables cross-request prefix reuse and retention; request-local KV allocation and retirement still follow the [cache contract](cache.md).
