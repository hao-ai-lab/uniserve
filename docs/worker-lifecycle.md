# Worker startup and service lifecycle

The caller owns the endpoint and Worker in one resource scope:

```python
from uniserve_worker.bootstrap.launch import (
    WorkerIpcEndpoint,
    endpoint_name,
    register_endpoint,
)
from uniserve_worker.worker import Worker

service = endpoint_name(config)
with WorkerIpcEndpoint(
    service,
    max_payload=config.ipc.max_payload_bytes,
    max_inflight=config.ipc.queue_depth,
) as endpoint:
    register_endpoint(config, service)
    with Worker.from_config(config) as worker:
        worker.bind(endpoint)
        worker.run()
```

The rank names its own endpoint and reports it to the head's registration address, which the launch descriptor carries; the head binds the rank's channel from that report. Reporting happens once the endpoint exists and before model loading, so the head establishes the bounded connection during startup. Worker resources close before the endpoint, and a failed model construction still closes it. The production entry is `uniserve_worker.bootstrap.launch.run_worker`.

## Construction and ownership

`Worker.from_config(config)` resolves the checkpoint through `uniserve_models`, loads its typed numerical composition through `uniserve.loading`, and constructs execution resources, physical storage, lanes and data-plane transports. Tokenizer, image processing and flow prompt assets remain with the worker's input consumers. It performs no numerical warmup or graph capture. Construction owns acquired resources until it successfully returns a Worker; a construction failure preserves the original exception and follows the aborted teardown contract below.

`Worker(model, ...)` accepts an already-loaded model and constructs the same execution resources without requiring IPC. ModelRunner resolves attention selection and binds persistent model inputs and workspaces before Worker measures the remaining memory grant. Request capacity is then resolved against that grant and shared by Worker and ModelRunner; sizing before those allocations would overestimate available storage.

`build_worker_layout()` combines model dimensions, component bindings, enabled calls, and lane admission limits into the final `WorkerInfo`. Resource allocation, warmup, and the IPC handshake consume that same report. The report advertises the encoder entry count and the maximum bytes per feature independently of total buffer-pool capacity; the scheduler bounds feature reservations by both limits. Admission limits do not reduce the storage reservations required by warmup and graph capture. Replacement uses the same launch configuration and compares each rank's resolved dtype, attention provider policy, weight and activation formats, capabilities, capacities and checkpoint identity. A replacement must establish a new endpoint incarnation while preserving those conditions; different placements can have different numerical policies.

The report also carries the checkpoint identity: a SHA-256 over every file of the checkpoint directory, taking each file's relative path and size and, for `.json`, `.jinja`, `.model` and `.txt` sidecars, the digest of its contents, while skipping hidden entries and the top-level `optimizer` and `original` directories. The head derives it once from a local checkpoint directory and states it in every rank's launch descriptor; each rank derives the identity of the checkpoint it actually loads, refuses to start when that differs from the head's expectation, and reports the loaded identity in `WorkerInfo`. The engine refuses an instance whose ranks report different identities, or an identity other than the head's expectation, naming the rank, its placement host and both identities. A Hub identifier yields no expectation on the head, so its ranks are held to one another's reports; the weightless stub model reports no identity.

Placement and communication requirements are resolved from one meta model before distributed initialization loads rank-local weights. `bootstrap.distributed.initialize_components()` creates the declared numerical groups and worker sampling groups in canonical order, including local meshes for temporal decoders. ProcessGroups owns the process groups and releases component groups before its default world; a process world supplied by the embedding caller is borrowed. `load_worker_model()` loads weights against these meshes, and ModelRunner binds resident numerical calls once. Triton selects its bundled assembler for the target GPU architecture; Worker does not modify compiler paths or probe system toolkit locations.

`from_config()` owns distributed initialization during construction and transfers that ownership to the returned Worker. A directly used `ProcessGroups` context drains on normal exit and retains potentially active groups for process teardown on exceptional exit. The outer Worker context owns the complete lifetime of the returned object.

Normal Worker context exit releases execution resources, pending results, graphs, model references, data-plane transports, and owned distributed resources. Cleanup attempts every release. Exceptional exit follows the aborted teardown contract below, with cleanup errors attached as notes to the original exception. If the body succeeded, a cleanup failure propagates normally. `close()` is idempotent and remains available to callers managing lifetimes explicitly with `try/finally`. A closed Worker cannot enter another context, bind, run, warm up, or execute.

The IPC endpoint remains caller-owned throughout. Worker removes completion notifications and its borrowed endpoint reference after asynchronous producers stop; Worker never closes the endpoint. Keep the endpoint open until the Worker context exits or `close()` finishes. Native endpoint `close()` is idempotent and rejects concurrent closure during an endpoint call.

## Binding and execution

`Worker.bind(endpoint)` borrows an open endpoint, initializes service queues and in-flight result state, registers completion notifications, and returns the same Worker. Binding the same or a different endpoint again raises without replacing the binding. A closed endpoint is rejected. Binding does not own resource cleanup.

`Worker.run()` requires a binding and permits one blocking invocation. It prepares fixed modules, performs numerical warmup and graph capture, exercises startup scenarios, and checks readiness before receiving any request, including `Info`. It then drives admission, dependencies, execution progress and response delivery in the calling process and thread. It does not create a service thread or child process. Existing execution resources may perform asynchronous CPU, transfer, and device work.

`run()` returning or raising does not close Worker. The surrounding resource scope owns cleanup, including failures from binding, warmup, service execution, or caller code. Let startup and runtime exceptions leave that scope; partially initialized or failed execution is not a retry contract. A second `run()` invocation is rejected even before scope exit.

Direct consumers use `Worker.submit(batch)` without binding IPC. It returns the BatchState owned by Worker. The caller drives `Worker.advance()` to progress dependencies, CPU work and retirement, then calls `Worker.poll(state)` to consume the batch's BatchOutput. A `None` result means the result is not ready. Continue advancing until it arrives; consuming that state again is invalid. Direct and IPC submissions share strictly increasing batch identities, queue capacity, launch order, collective participation and local-product dependency checks. A full direct queue raises `ResourceError` without consuming the proposed identity; consume a result before retrying. Keep the Worker scope alive throughout this process.

Explicit `warmup()` is optional for direct execution and must precede the first serving submission; full graph policy captures required configurations on first use before the catalog is sealed. Successful warmup is retained for the Worker's lifetime and reused by a subsequent `run()`; warmup failures leave cleanup to the owner. Warmup prepares numerical providers and graph captures, exercises synthetic requests, retires startup collective identities, and checks device memory grants before marking readiness. Successful scenarios retire their synthetic requests through the ordinary execution protocol. A failed scenario propagates its error immediately and leaves resource release to the enclosing Worker scope.

## Protocol and shutdown

Each submission batch is submitted once and answered once. A batch carries one computation through one component. BatchState directly owns its execution stream, completion buffer and publication state; result visibility and physical retirement remain separate. Completed results cannot be collected again. Duplicate submissions return `InvalidDescriptor` before applying admissions, commands, or computation. Native IPC constructs typed request records from validated wire fields; mapping inputs use the Python parsing boundary.

IPC version 68 requires a matching Rust frontend and Python native extension. Version mismatch is rejected at the transport boundary; rebuild both artifacts together. Request identity is `(engine_id, request_id, request_epoch)`; retained buffers keep the exact originating identity across request-slot reuse. Each computation is identified by its `(batch_id, request_index)`, preserved when a batch is split across the ranks of its component. Every call also states the coordinates its call assumes — logical position, KV visible and computed lengths, and flow step — and a call whose coordinates contradict the request's recorded progress is refused.

`batch_id` values strictly increase in each Worker's submission order, including direct Python calls. Worker stores one high-water mark for service admission; no completed-batch history is retained. Successful startup retires its synthetic requests and identity scope before service admission begins. The Rust executor allocates a batch identity when it assembles the batch, and dispatches it to the ranks of the one component it addresses. Batches may become ready out of order, and each response retains its own `batch_id`. ID gaps are valid. Counter exhaustion is an error. Waiting timeouts continue waiting on the original transport request; they never submit it again. Rank death uses the existing scoped failure and replacement handling, retiring affected work rather than resubmitting its batch.

Worker advances dependency-ready work in submission order within available execution and transport credits. It assigns no priority by call kind. Asynchronous input preparation and independent completions can overlap; shared request state and cooperative collectives retain their correctness ordering. `Free` revokes acquisition on acceptance so a pending allocation cannot prevent its release; acknowledgement still waits for existing physical readers to retire.

The service preserves configured payload bounds, queue depth, backpressure and ready-response delivery. `queue_depth` bounds the batches in flight on one rank, and in-flight execution occupies that capacity. `Close` stops admission and acknowledges after accepted work, delivered responses, and safe retirement drain. Protocol errors retain the existing error response and fatal-shutdown behavior.

`Close` ends request processing; resource release follows when the owning scope exits. Request shutdown through this protocol rather than closing an endpoint underneath a running Worker. Cyclic garbage collection is temporarily disabled only during the request loop and restored before scope cleanup.

## CallKind bindings

ComponentBinding contains placement and borrowed numerical calls. Each lane references its call and owns its mutable input buffers and execution context. Each CUDAStream retains its physical stream and dependency events; a partitioned stream owns a Green Context or borrows its parent's SM allocation, and child streams close before their parent. Prepared execution owners retain graph buckets and pools; text, module and denoising calls share graph capture, input copying and retirement. Denoising trajectories bind named slot spans and static numerical inputs once, then select a step and update live tensors for replay. Prepared shapes and resident graph buckets each retain their own capacity limit. Calls on one numerical entry serialize access to its workspace and graphs; independent entries receive separate streams and mutable resources while sharing parameters.

Green Context bindings enqueue computation and communication within their assigned SM partition, including graph capture. Streamed communication uses a transport stream in the same context, with producer and consumer dependencies. Default full-device execution retains its process-group and peer-reduction providers. Communicators borrow their physical backend groups from ProcessGroups; independent groups with identical topology retain distinct ordering domains.

Warmup, capture, eager execution and graph replay use these same bindings. ModelRunner groups homogeneous numerical inputs by actual capability, component, device, stream and shape, then returns outputs aligned to their call indices. Batch retains the submitted protocol columns. Each batch selects its component's stream before binding inputs and carries that stream through output capture, publication and failure retirement. Computations whose predicates are false reserve no numerical resources. Construction rejects unsupported or conflicting bindings without changing the requested graph or device policy.

Products move by one device mechanism and one host mechanism, and a product's location decides which carries it. A device product is published where it lies when its storage is an exportable CUDA physical allocation, and otherwise copied into the rank's bounded VMM pool; a product that fits neither travels as host bytes. A consumer imports the publication's shareable allocation handle directly and reads through its own mapping, so device products cross hosts wherever the device exports a fabric handle. A host product travels in a shared-memory segment within a host and on the rank channel across hosts, and is published over each of the two that reaches a consumer the producing call names, so a product read only on its own host never enters the channel. A segment carries its own header: the digest of the locator that names it, a readiness word the producer writes after the payload, and one acknowledgment word per rank of the instance. A consumer checks the digest, claims its word, waits on the readiness word, copies the payload out or reads it in place, and acknowledges its word; a pool chunk's header carries the same words, claimed and acknowledged on the consumer's read stream around its copies. The producing rank retires a segment, and returns a pool chunk to its pool, once the engine has released the buffer and every consumer that claimed it has acknowledged, sweeping those words on its retirement passes; a consumer that never claimed it, such as the reader of a request cancelled before that call was submitted, holds nothing, because the engine releases a buffer only after every consuming call has resolved or will never be submitted. No connection back to the producer is needed. Within a host, device readiness is an interprocess event; across hosts the producer synchronizes its stream before publishing. Source allocations, read capacity and published storage remain retained through physical completion. These transfers do not require source and destination processes to share device ordinals.

Normal cleanup drains computation and abandons unsubmitted output work. Submitted CPU jobs finish before their mux sessions close. Graphs release before their backing storage and attention metadata; pinned staging and retained views release while producer streams are still alive. Streams and Green Contexts close after those consumers, and ProcessGroups closes last. Free and Finish revoke logical acquisition while storage and transfer owners retain existing readers until physical completion permits reuse. A cancelled or failed shared-memory read acknowledges its claim when its last actual access ends, even if the producer never became ready.

Exceptional scope exit and `close(aborted=True)` stop admission, detach completion notifications, terminate codec processes and abort local communicator bindings without waiting for device work or peers. Graphs, streams, process groups and their borrowed storage remain retained until process exit; aborted teardown never reports those accesses as physically retired. This process must terminate and must not create another serving runtime. The worker CLI reports the failure and exits directly, avoiding interpreter finalizers that would wait on failed transfers. Python embedding callers must likewise terminate the failed process.

Token, diffusion, vision and image-decoding rows have distinct numerical inputs. Token and diffusion staging share attention-column copying; image codecs allocate only request-slot columns and borrow their already placed tensor views. Batch buckets, standalone method signatures and denoising ladders retain their numerical capture catalogs, while one `GraphMemory` owner accounts for their device pools, static inputs and prepared workspaces against the common byte budget. New captures are checked before becoming resident, and replay does not inspect allocator state. Denoising uses its component's lane with either eager execution or graphs.

Encoded video product bounds follow the serving libx264 baseline CAVLC syntax and MP4 container limits, including padded macroblocks, NAL escaping, slice headers and sample tables. Reservations therefore cover high-entropy frames without changing codec quality settings. `encoded_video_bytes()` owns this bound next to the encoder policy; the media product layer adds its length prefix.

## Model loading and diagnostics

Weights remain fixed for a Worker's lifetime. Loading, quantization and model identity are established at construction; changing weights requires a new Worker. The loader accepts `auto`, `safetensors`, `pt`, `dummy`, and `layered`. Standard indexed safetensors shards, component sources, parameter conversion and runtime tensor/pipeline partitioning share the ordinary component loading path.

`graph_policy` (`--graph-policy off|auto|full`) is the graph master switch. Prefill graph eligibility, shape buckets and memory tuning remain separate settings. Captured graphs live with their computation bindings and release on shape replacement or Worker closure.

`--video-graph-shapes` declares the video request shapes, as `SECONDSxTOKENS` items, whose denoising ladders warmup makes resident before the worker reports ready. Each numerical trajectory owns a graph per ladder step, shared across request slots through fixed gather/scatter staging. A shape a deployment does not declare still serves; its first request captures the missing ladder. The declared shapes also bound how many numerical sizes and graph buckets stay resident, so declaring more shapes than a deployment serves costs startup time and device memory.

Encoded video products reserve host storage from the default x264 encoder's conservative macroblock bound, including partial macroblocks, bitstream escaping and container overhead. Admission therefore does not assume that generated frames compress well. This reservation can be substantially larger than the resulting MP4; deployments must budget host product capacity for the declared video dimensions and concurrent requests.

Media units are encoded and the artifact is assembled on a host worker: a worker whose ranks run on the host with no device, placed by the same document as the model worker and holding the `video_encoder` and `muxer` components. A video decoding round converts each media unit to RGB on the rank that decoded it and publishes it as a host product over shared memory; a host rank's encoder reads that segment in place, by name and offset, so a media unit reaches its encoder without a copy, and acknowledges the segment once the encode has read it. The encoded unit rows are the host rank's product, published when its encodes complete, and the muxer rank assembles them with the audio track; the PCM timeline is imported like any product, since its decoding ranks may be on other hosts, and staged in a segment of the muxer rank's own for its codec. Host work runs in codec processes the host rank starts alongside its own interpreter, one per media unit it encodes at once plus one for the muxer, so no encoder or container runs under a rank's interpreter lock: closing an x264 encoder joins its thread pool, and inside a process that also drives a device that join takes hundreds of milliseconds and would stall every device launch and completion report. A request's mux session lives in the codec process that first receives it, and the artifact is published to shared memory from there. A host rank reports ready once every codec process has answered a probe that loads its codecs; a rank of the model worker starts no codec process. A decoded media unit must be encoded on its own host: the engine refuses at startup a placement whose encoder rank for a unit is on another host than the rank decoding it.

`UNISERVE_TORCH_PROFILER_DIR` enables PyTorch capture. `UNISERVE_PROFILE_ACTIVITIES` selects `CPU,GPU`, and `UNISERVE_PROFILE_START_STEP` / `UNISERVE_PROFILE_STEPS` select the execution window in steps, where one step is one submitted batch that carries calls; lifecycle-only batches are not counted. Each step appears in the trace and as an NVTX range named `batch:<kind>:<component>`, for example `batch:denoising:denoiser`. Nsight and the PyTorch profiler cannot share one process's CUDA activity collection, so capture them in separate runs. Prefix, stack and shape recording use `UNISERVE_PROFILE_PREFIX`, `UNISERVE_PROFILE_WITH_STACK` and `UNISERVE_PROFILE_RECORD_SHAPES`. `UNISERVE_CUDA_PROFILER` controls the CUDA profiler API within that window. `UNISERVE_NVTX` independently enables NVTX ranges. Normal errors and forward statistics remain available without a custom event recorder.

For Python call profiling, set `UNISERVE_DIAGNOSTIC_DIR` and pass `--worker-python scripts/profile_worker.sh` to the server. This dedicated launcher runs the standard `cProfile` module around the complete Python process, including model loading and warmup, and writes one `.pstats` file per process on normal exit. Close the server gracefully to flush the file. Worker has no call-profiler window or fault-injection controls; failure tests terminate their child processes externally.
